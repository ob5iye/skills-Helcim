## Jira concepts learned (how they fit together)

- **Status ≠ board column.** A status exists only when added to a *workflow*; a card appears on the board only when the status is *mapped to a column* (board → Configure board → Columns). Unmapped status = invisible on board.
- **Status names are global** across the whole site. Before creating a status, search Workflow Items → Statuses — e.g. "Monitoring" already existed (category In Progress); we reused it. Never create near-duplicates like "Monitoring 2".
- **Category matters for reporting**: To Do / In Progress (yellow) / Done (green). A "watching" state should usually be *In Progress* category so it does not count as complete in reports/burndowns, and `Set resolution` must stay unchecked on its board column (only Done columns set resolution).
- **Company-managed ("classic") projects**: statuses added via workflow edit + publish, NOT from the board. Team-managed projects: columns added directly from board.
- **Workflow sharing = the #1 risk.** Before editing ANY workflow: Global settings (⚙️) → Work items → Workflows → search the workflow → check "Included in Space(s)" and "Included in Workflow Scheme(s)". If shared with other projects, COPY it first and assign the copy, never edit in place.
- ⚡ **Lightning bolt in the workflow diagram = a global "Any" transition** (any status can move into this status). No arrows between statuses = everything moves freely. When adding a status to such a workflow, tick "Allow all statuses to transition to this one" — movement OUT is already covered by the other statuses' Any transitions.
- Workflow edits only apply on **Publish**; choose "Save a backup copy" for one-click rollback. Discard draft = zero risk while editing.
- Kanban backlog panel (if board has one) is separate from the Backlog column.

## Forms & automation — Operations learnings

### Core constraint: there is no "Form submitted" automation trigger

Jira Software / Work Management projects do **not** offer a "Form submitted" trigger.
That trigger is exclusive to Jira Service Management projects. This is by design, not a
board misconfiguration and not something to raise a support ticket for.

**The workaround: Jira auto-labels form submissions.**

When a Jira form creates a work item, Jira automatically stamps two labels:

```
["form", "form-<formID>"]
```

`<formID>` matches the number in the builder URL: `/jira/software/c/projects/<KEY>/form/<formID>/builder`.

Verified examples:
- Form 818 (Equipment Request Form) → `form-818`
- Form 1325 (Elavon Card Scheme Registration) → `form-1325`

So the pattern for "run automation when a form is submitted" is:

1. **Trigger:** `Work item created`
2. **Condition:** `Work item fields condition` → Field `Labels`, Condition `contains any of`, Value `form-<formID>`
3. **Action:** whatever the request needs

Never trigger on work item **type** alone. Forms usually create plain `Task`, which is also
the type humans create manually — filtering on type would hit every manual task on the board.

Fallback if `Labels` offers no `contains` operator: use the `Work item matches JQL` condition
with `labels = "form-<formID>"`.

**Safe failure mode:** if the label guess is wrong, the flow simply never fires. It cannot
misfire onto unrelated items. So it is safe to enable before verifying with a test submission.

### Board filters can silently hide items — always read the filter first

Before automating anything, read the target board's filter JQL. A board's filter determines
whether automation output is even visible, and which fields must never be touched.

Real example — the **OPS: Card Brands and Acquirers** board:

```jql
"Team[Team]" IS EMPTY AND project = OPS ORDER BY created DESC
```

Consequences:
- New OPS items appear on this board automatically (no Team set), so "put it on this board"
  needs no configuration at all.
- **Never set the Team field** on OPS items via automation or a form field. Doing so removes
  the item from this board instantly.

Also note the Operations space has multiple boards (Card Brands and Acquirers, Special
Projects, Supply Chain) that likely partition by the same Team field.

### Date smart values

```
{{now.plusDays(1).jiraDate}}          next calendar day
{{now.plusDays(45).jiraDate}}         45 calendar days out
{{now.plusBusinessDays(1).jiraDate}}  next business day (skips weekends)
```

Chain them for relative-to-relative dates, e.g. start date + 45 days:
`{{now.plusBusinessDays(1).plusDays(45).jiraDate}}`

Confirm requirements literally — "next day" and "next business day" differ, and "45 days out"
vs "45 days from the start date" differ by a day. Ask the requester rather than inferring from
surrounding text.

### Reporter already captures who submitted a form

Do **not** create a custom field for "who is requesting". Jira records the submitting user as
the **Reporter** automatically, and it is visible on boards/list views and filterable.

Verified: OPS-425 → Reporter Chris De Sousa; OPS-424 → Reporter Alexis David (both from form 818).

Only add something extra when people submit *on behalf of* someone else. Prefer a form-only
question over a new Jira custom field — new custom fields can propagate through shared screen
schemes and affect other projects.

### Working with forms

**Builder view vs live view** — in the builder, every input is greyed out and shows placeholder
text ("Answer will be written here", "Date will be entered here", "Unassigned"). That is normal
and does **not** mean the field is broken or read-only; you simply cannot submit from the builder.

To open the submittable form: Forms tab → **⋯** on the form card → **Copy link / Share**, or the
**↗** icon in the builder toolbar.

**Reading a form's config:** the Forms tab card shows the work item type it creates on a chip
under the form name. The builder URL contains the form ID needed for the label condition.

**Fields available to drag onto a form** (OPS): Components, Fix versions, Labels, Parent, Priority,
Sprint, Story Points, Team — plus whatever is already placed, and "Edit custom fields" for more.
Assignee, Start date, and Due date can also be present as questions.

**Do not add Team to an OPS form** — see the board filter section; it hides the item.

**Form question → Jira field mapping** is shown beneath each question label in the builder.
Example from form 1325:

| Question | Maps to |
|----------|---------|
| Merchant DBA Name (required) | Summary |
| MID | Description |
| Completed Elavon Card Scheme Registration PDF | Attachment |
| Assignee / Start date / Due date | the matching Jira fields |

Form questions can also be left unmapped, storing the answer only in the form attached to the
issue. That is the zero-risk way to collect extra info without creating a custom field, at the
cost of not being filterable in JQL.

### Flows UI navigation

- Path: **Space settings → Automation → Create flow → Create from scratch**
- Prefer "Create from scratch" over "Create with Rovo" when the spec is already known: Rovo may
  translate "when the form is submitted" into "when a Task is created", widening the blast radius.
  AI-powered steps also consume Rovo credits.
- Rename via the pencil icon next to the flow name; then toggle Disabled → **Save and enable**.

### Keeping changes isolated to one board

1. Create flows from **Space settings → Automation**, never from Global administration. The
   flow's Scope column must show the single space.
2. Condition on the `form-<formID>` label so the flow fires only for form submissions, not for
   manually created items of the same type.
3. Do not edit shared schemes, screens, or create global custom fields.
4. Do not modify other people's existing flows — back out with the ← arrow, never Save.
5. Flows act only on items created after enabling; nothing is retroactively changed.

### Verifying via API instead of clicking

After a test submission, read the result directly rather than hunting in the UI:

```
searchJiraIssuesUsingJql
  jql: "project = OPS ORDER BY created DESC"
  fields: ["summary","labels","assignee","reporter","duedate","created","customfield_10015"]
  maxResults: 3
```

`customfield_10015` is **Start date** in this instance. `duedate` is Due date.

Test method: submit the form leaving the automated fields **blank**. Blank-on-submit proves the
flow populated them rather than the tester. Then delete the test item in the UI (deletion is
destructive — always have the user do it and confirm first).

- **Credential creation choices**: API token vs OAuth 2.0 — pick API token when the tool uses basic auth (`email:token`); OAuth 2.0 only if their code implements the flow. Scoped tokens may require the gateway URL `https://api.atlassian.com/ex/jira/{cloudId}/...` instead of the site URL — flag this to integration owners.
- Scope minimal: read:jira-work + write:jira-work (classic) is the safe granular-equivalent set for read-issues/post-comments bots.
