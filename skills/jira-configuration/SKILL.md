## Jira concepts learned (how they fit together)

- **Status ≠ board column.** A status exists only when added to a *workflow*; a card appears on the board only when the status is *mapped to a column* (board → Configure board → Columns). Unmapped status = invisible on board.
- **Status names are global** across the whole site. Before creating a status, search Workflow Items → Statuses — e.g. "Monitoring" already existed (category In Progress); we reused it. Never create near-duplicates like "Monitoring 2".
- **Category matters for reporting**: To Do / In Progress (yellow) / Done (green). A "watching" state should usually be *In Progress* category so it does not count as complete in reports/burndowns, and `Set resolution` must stay unchecked on its board column (only Done columns set resolution).
- **Company-managed ("classic") projects**: statuses added via workflow edit + publish, NOT from the board. Team-managed projects: columns added directly from board.
- **Workflow sharing = the #1 risk.** Before editing ANY workflow: Global settings (⚙️) → Work items → Workflows → search the workflow → check "Included in Space(s)" and "Included in Workflow Scheme(s)". If shared with other projects, COPY it first and assign the copy, never edit in place.
- ⚡ **Lightning bolt in the workflow diagram = a global "Any" transition** (any status can move into this status). No arrows between statuses = everything moves freely. When adding a status to such a workflow, tick "Allow all statuses to transition to this one" — movement OUT is already covered by the other statuses' Any transitions.
- Workflow edits only apply on **Publish**; choose "Save a backup copy" for one-click rollback. Discard draft = zero risk while editing.
- Kanban backlog panel (if board has one) is separate from the Backlog column.

## Change history

### 2026-09-04 — Added "Monitoring" status/column to Legal board (requested by Stephanie)
Full procedure used — reuse for any future status request:
1. **Inspect (read-only)**: Project settings → Workflows → note scheme + workflow name + issue-type mapping. Global ⚙️ → Work items → Workflows → check "Included in Space(s)/Scheme(s)" for sharing.
2. **Status**: found existing global "Monitoring" (In Progress category) → reused. (If absent: Statuses → Create status, category In Progress, plain description.)
3. **Workflow edit**: ⚙️ → Work items → Workflows → workflow row → ⋯ → Edit → Add status → pick existing from dropdown → ✅ "Allow all statuses to transition to this one" → **Publish with backup copy**.
4. **Board**: board → ⋯ → Configure board → Columns → Add column → rename `Monitoring` → drag between IN PROGRESS and DONE → drag Monitoring status from Unmapped panel into it → leave "Set resolution" unchecked, Min/Max None (auto-saves).
5. **Verify**: open ticket → status dropdown → Monitoring (card jumps to column) → drag back → restore original status.
6. Notify requester. Result confirmed working.

### 2026-09-09 — LEGAL-100 "can't view" investigation: it was **deleted**, not a permissions issue
Symptoms: assignee + project admin (Reggie L.) + org admin all unable to open LEGAL-100 while board worked fine. Ruled out issue security (no scheme on LEGAL) and project roles. **Jira audit log (⚙️ → System → Audit log, search the issue key) showed: `Deleted Jira issue`, author Abdi Obsiye, 07/Sep/26 2:28 PM.** Learnings:
- Deleted issues surface the SAME "We can't show this space / may not exist" error as permission blocks — check the **audit log first** when a single issue vanishes for everyone.
- Jira Cloud has **no recycle bin**; recovery only via Atlassian support backup restore (act within days).
- Org admin ≠ site admin ≠ project Browse permission — three separate layers; elevate via admin.atlassian.net (`site-admins` group) before deep debugging.
- Project `Administrators` role does NOT bypass issue security levels; only `site-admins` do.
- Follow-up hardening: scope `Delete Issues` permission to site admins only in shared permission schemes (accidental delete risk).

Jira app role = User; project permissions: Browse + Add Comments only. Migration done when token's "Last used" flips from "Never used" → then revoke the old shared credential on Jira-Integrations.
- **Credential creation choices**: API token vs OAuth 2.0 — pick API token when the tool uses basic auth (`email:token`); OAuth 2.0 only if their code implements the flow. Scoped tokens may require the gateway URL `https://api.atlassian.com/ex/jira/{cloudId}/...` instead of the site URL — flag this to integration owners.
- Scope minimal: read:jira-work + write:jira-work (classic) is the safe granular-equivalent set for read-issues/post-comments bots.
